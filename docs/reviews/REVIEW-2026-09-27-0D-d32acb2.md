  40% of the canvas stays visible. It shrinks the panel, not the gutter.
- **Rail margin.** `brushPanelPlacement` sets a minimum gutter of `TOOL_RAIL_GUTTER_DP = 64`.
- **Preview column.** `brushCategoryRailWidthDp` keeps at least a 72dp preview column.

| 360 × 640 | 152 | 144 | 40% | 56 (96) |
| 640 × 360 | 320 | 256 | 40% | — |

| 1280 × 800 | 454 | 756 | unchanged | — |

Other points:

- `BrushPanel.onStart` now reads `Configuration.screenWidthDp/screenHeightDp`
  (`BrushPanel.kt:82-101`), which describe the app window in multi-window mode. This addresses the
  `displayMetrics` concern.
- The bottom margin is now 16–24dp (`:90`), which closes R9.
- `PanelGeometryTest` now contains both AC1 sizes, checks both dock sides (placement uses absolute
  `Gravity.LEFT`, so this covers RTL and LTR), and asserts the 40% rule and the preview column.

### R2: preview threading. Resolved in code

- **Scope.** A `SupervisorJob` + `Main.immediate` scope is created in `onCreateView` (`:127-128`)
  and cancelled and nulled in `onDestroyView` (`:384-387`). The adapter is detached first.
- **Cancellation.** Each holder cancels its job when rebound (`:709`) and when recycled (`:799-800`,
  which also clears the tag). Detaching the adapter cancels every job that is still active
  (`:806`). This covers the stale-row case from the first review, where a set switch replaces the
  adapter.
- **Placeholder and fade.** A neutral placeholder (`:774`) is followed by a 100ms fade-in (`:783`),
  within the ≤120ms budget.
- **Errors.** `OutOfMemoryError` is caught, logged, and `trimCache()` drops references without
  recycling bitmaps that may still be on screen (`:787-789`, `BrushPreviewRenderer.kt:117-120`).
  Other exceptions are logged. Cancellation is rethrown.
- **Thread safety.** Completion handlers mutate `activePreviewJobs` on the main thread: the coroutine
  resumes on `Main` after `withContext(Default)`, and the job is added before its handler is
  registered. The old process-wide executor is gone. No unsafe interleaving was found.

### N1: `dockSheet` behaviour dropped from the brush panel (S3, fix before the device check)

`3228527` called `PanelUi.dockSheet(...)` in `BrushPanel.onStart`. `d32acb2` replaced it with
`PanelUi.expandSheet(bottomDialog, peekDp = panelHeightDp)` (`BrushPanel.kt:94`). `expandSheet`
(`PanelUi.kt:454-471`) only sets the height, `STATE_EXPANDED`, `skipCollapsed` and the peek height.

The brush panel therefore no longer gets these parts of `dockSheet` (`PanelUi.kt:479-521`):

- **`isDraggable = false` (`:519`).** `BottomSheetDialog` is hideable when cancelable, and
  `isCancelable = true` (`BrushPanel.kt:87`). A downward drag on the panel, or an over-scroll past
  the top of one of its two lists, can now slide the sheet away and dismiss it. The spec (UX
  behaviour, AC8) allows dismissal only by an outside tap, Back or explicit close.
- **`enterImmersiveMode(window)` (`:502`).** The dialog window no longer hides the system bars, so
  opening the brush panel may bring the status and navigation bars back over the canvas.
- **Side-panel window animation (`:503-507`).** The docked panel may now use the default bottom-sheet
  slide-up animation.
- **Transparent window background (`:501`) and the sheet's surface setup (`:509-516`).** These are
  probably harmless, because `BrushPanel` makes the sheet transparent itself (`:108-110`), but they
  are unverified.

Six other panels still use `dockSheet`: Adjustments ×2, Brush Studio, Color picker, Actions and
Urban. The brush panel is now the only docked panel with different chrome behaviour, which is the
opposite of the spec's "one panel geometry system".

**Required:** call `PanelUi.dockSheet(dialog, dockSide, widthDp = placement.widthDp)` again, then
apply the `brushPanelPlacement` size and position as now. Alternatively, move the non-geometry
parts of `dockSheet` (drag lock, immersive mode, animation, background) into a helper that both
paths call. Add a check to the device script that dragging the list down at its top does not
dismiss the panel.

### N2: the rail gutter is a constant, not the rail (S4, device check)

`TOOL_RAIL_GUTTER_DP = 64` (`PanelGeometry.kt:11`) is the minimum gutter, and
`narrow split screen preserves the tool rail gutter` asserts that the gutter is at least that same
constant. The real footprint of the right-hand rail in RTL is:

- **Tablet XML:** 16dp margin + 10dp padding + 48dp slider + 10dp padding = **84dp**
  (`activity_canvas.xml:256-277`).
- **Compact phone at runtime:** 8dp margin + 42dp slider = **50dp** (`CanvasActivity.kt:1257-1275`).

On a tablet about 1393dp wide (the Tab S9 Ultra at default density), the gutter is
`1393 × 0.055 = 76dp`, so in Arabic the panel may overlap the rail by about 8dp. This formula
predates 0D. Only the "preserves the rail" claim is new.

**Required:** verify on both devices. Preferably derive the gutter from the rail's measured bounds
instead of a constant.

### N3: usability of a 152dp palette (S3, device)

At a 360dp window width the arithmetic meets AC1, but the whole brush palette is 152dp wide: a
56dp rail and a 96dp preview column. The header, the "Import" control, the set cover card and the
two-line brush rows were designed for 330dp or more.

**Required:** a screenshot at about 360dp split-screen in Arabic and English. If it is not usable,
record the owner's decision on a floor (for example, switch to the compact single-column layout
below a width threshold).

### N4: latent `IllegalStateException` after `onDestroyView` (S4)

`updateBrushes()` uses `checkNotNull(previewScope)` (`BrushPanel.kt:492`). It is called from
`lifecycleScope.launch { repository.all.collect { … updateBrushes() } }` (`:348-366`). That scope
lives for the fragment, not the view. `onDestroyView` nulls `previewScope` (`:387`), so a Room
emission between `onDestroyView` and `onDestroy` would throw.

For a normal dismissal both callbacks run in one fragment transaction, so the window is narrow.
The fix is still one line: collect on `viewLifecycleOwner.lifecycleScope`, or return early when
`previewScope == null`.

### N5: parallel, non-cooperative rendering (S4, measure under AC7)

`withContext(Dispatchers.Default)` (`:777`) lets several rows render at once during a fling. A
render that has started cannot be interrupted, so a few renders may finish after the panel closes.
This is bounded and acceptable, but AC7 (no frame over 32ms caused by previews) should be measured
with it in place.

Related, outside R2's row scope: the set-cover montage is still rendered synchronously on the UI
thread (`:482`).

## Problem and user value

The Plan 1 exit gate needs proof that every supported version of a user's data opens correctly and
that no crash point loses work. Today Room has `exportSchema = false`
(`ArtworkDatabase.kt:71`), so there are no schema snapshots to migrate from in tests. Version 1 is
destructively dropped (`:111`). No project-format migration fixtures exist beyond the codec's
version switch (`ProjectDocumentCodec.kt:44-56`).

## Scope

1. **Room schema export.** Set `exportSchema = true` with `room.schemaLocation` pointing at
   `app/schemas/`, and commit the JSON for v4. Reconstruct **v2 and v3** schemas from
   `MIGRATION_2_3`/`MIGRATION_3_4` (the only history available, because the repository starts at
   v4), and ideally cross-check them against a database pulled from a device that still runs an older
   build. Commit them as test fixtures,
   clearly labelled "reconstructed".
2. **Room v5 migration** (additive): add `modifiedAt INTEGER NOT NULL DEFAULT 0`, backfilled from
   `createdAt`, and `deletedAt INTEGER` (nullable). Switch the gallery query to
   `ORDER BY modifiedAt DESC` with `WHERE deletedAt IS NULL`, and make saves stop overwriting
   `createdAt`. This fixes 1A D8 without changing the order the user sees, because the backfill keeps
   today's effective order.
3. **Version 1 policy.** Keep `fallbackToDestructiveMigrationFrom(1)`, because v1 never shipped
   editable projects. Before the drop, a v1 database's `artworks` rows get their PNG files moved into
   a "Recovered images" import list, so no image becomes invisible. The product owner confirms that
   v1 never reached users. If it didn't, this step is a documented no-op.
4. **Project-document fixtures.** Commit a small fixture per supported `schemaVersion` (1–4 and the
   1A version) under `app/src/test/resources/projects/`. They are generated by a test utility, not
   taken from user art. Also add decode, validate, load and re-save round-trip tests.
5. **Failure-injection suite.** Using 1A's `FileOps` hook, inject a fault at every checkpoint:
   `ENOSPC` on each file write, `EIO` on fsync, permission loss on the project directory, a process
   kill (simulated by abandoning the coroutine at the checkpoint), and a corrupt or truncated file on
   the next read. Each case asserts that the prior revision or the new revision is intact and that the
   1C health state is correct.
6. **Stress.** 100 randomized save/reopen cycles (seeded) with layer add, delete, reorder, resize and
   mask changes. Every cycle compares per-layer checksums against an in-memory oracle.

## Non-goals

- Cloud schema and sync conflicts (Plan 6).

## Technical design notes

- Room migration tests use `MigrationTestHelper` (instrumented), because Room's helper requires the
  Android runtime. Project-store fault injection runs on the JVM with Robolectric (for
  `Bitmap`/`BitmapFactory`) through `FileOps`, keeping the loop fast enough to run 100 cycles in CI.
- Seeds are printed on failure, so every failure is reproducible with `-Dartify.seed=<n>`.

## Data migration and rollback

Scope 2 is the only user-visible migration, and it is additive. Rolling back to a v4 build after v5
has run requires Room's downgrade path, which is not supported. So v5 ships only once 1A–1C are
accepted, and the release notes say so.

## Acceptance criteria

1. Committed Room schemas exist for v2 (reconstructed), v3 (reconstructed), v4 and v5.
   `MigrationTestHelper` tests pass for 2→5, 3→5 and 4→5, and row content is preserved.
2. After v5, the gallery shows the same order as before on a fixture database, and saving no longer
   changes `createdAt`.
3. Every project schema fixture decodes, validates, loads and re-saves. Re-saving and reloading is
   identical at the pixel level.
4. All fault cases in scope 5 pass: never a mixed revision, and never a healthy-looking damaged
   project.
5. 100/100 stress cycles pass on three different seeds in CI.
6. The suite runs in the required gate, and its runtime is recorded (target: JVM part under 3
   minutes).

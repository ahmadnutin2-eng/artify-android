# Phase 0B — Baseline measurement harness

- Status: Draft. Needs product-owner approval.
- Planner owner: Claude (Planner)

- Reviewer owner: Independent
- Base commit SHA: `5941ab1c48a384ed2d3ff073e538398da56fa98f`
- Dependencies: a clean clone that builds (0A). A POSIX `gradlew` is needed for Linux CI (see 0C D3).
- Affected areas: new modules `:benchmark` (Macrobenchmark) and `:screenshot` (or a screenshot source
  set in `:app`), `app/build.gradle` (test dependencies only), `app/src/test/**`,
  `app/src/androidTest/**`, `docs/baseline/**`. **No production behaviour changes**, apart from adding
  trace sections (`androidx.tracing`) that compile to no-ops when tracing is off.

## Problem and user value

The roadmap requires every later phase to be judged against saved numbers, not opinion. Today there
are 29 JVM and 2 instrumented test classes and no performance, latency or screenshot baselines, so
0D, 1A and 2A cannot prove they improved anything or broke nothing.

## Scope

1. **Reference device matrix**, recorded in `docs/baseline/DEVICES.md`: small landscape phone
   (≤ 400dp tall in landscape), flagship phone, 8–11" tablet, and a stylus device (may be the tablet).
   For each: model, Android version, refresh rate, RAM, and whether it has a stylus. The product owner
   names the physical devices; emulator profiles mirror them for CI.
2. **Measurement protocol** in `docs/baseline/PROTOCOL.md`: build variant (`release`-like
   `benchmark` build type, minified, non-debuggable), warm-up (3 runs discarded), iterations (10),
   thermal rule (start below 35°C battery; pause if throttled), refresh rate fixed at the device
   maximum, airplane mode, the same test document set, and how results are stored (JSON under
   `docs/baseline/results/<date>-<device>-<commit>.json`).
3. **Macrobenchmarks** (`:benchmark`, AndroidX Macrobenchmark):
   - `StartupBenchmark`: cold and warm start to the gallery's first frame.
   - `OpenProjectBenchmark`: gallery tap to the first canvas frame for the reference documents.
   - `StrokeBenchmark`: injected `MotionEvent` stylus strokes (a short one, a long fast one, and a
     pressure ramp) on a 4096² × 20-layer document with a textured brush. Reports frame duration
     p50/p90/p99 and the percentage of janky frames.
   - `PanBenchmark`: two-finger pan and zoom on the same document.
   - `BrushPanelBenchmark`: open the brush panel cold and fling the whole library (needed by 0D
     AC7).
4. **In-app trace sections** (`androidx.tracing:tracing`): `Stroke.process` around the per-sample
   path in `DrawingView`, `Stroke.render` around the per-frame composite, `Save.snapshot` and
   `Save.write` (1A), and `Preview.render` (0D). The benchmarks read these with `TraceSectionMetric`
   so stroke event processing p95 (target < 4ms) is measured directly.
5. **Input-to-pixel latency protocol** (manual, for stylus devices): a 240fps camera recording of a
   ruler stroke, counting frames between tip contact and pixel appearance. Five runs, median
   reported. This is documented and not automated, as `ACCEPTANCE_CRITERIA.md` allows.
6. **Golden screenshots.** JVM screenshot tests (Paparazzi or Roborazzi; the Executor picks whichever
   supports AGP 9.1 and records the version) for gallery, canvas chrome, brush panel, layers panel,
   colour panel and Brush Studio. Each renders in Arabic and English, at 360×800, 800×360, 600×960 and
   1280×800 dp, at font scale 1.0 and 1.3. They run on Linux, so the cloud agents can check them
   without a device. The threshold is at most 0.1% of pixels differing by more than 8/255 per channel.
7. **Reference documents** generated by a debug-only fixture builder (not committed binaries):
   `doc-small` (1080², 3 layers), `doc-large` (4096², 20 layers, with masks), and `doc-urban` (an
   urban project with 200 elements).
8. **Baseline report** `docs/baseline/BASELINE-<date>.md`: the first full run on the current `main`,
   including failures. This report is what later phases compare against.

## Non-goals

- Fixing any performance problem found (each goes to its plan: 2A input, 2B render, 3A panels).
- Crash analytics or field telemetry (Plan 8B).

## Technical design notes

- The `benchmark` build type extends `release`, uses debug signing, and sets
  `profileable` (`<profileable android:shell="true"/>`). This lets the sidecar application id suffix
  pattern already used for QA builds (`applicationIdSuffix ".codexqa"`) stay separate from the
  benchmark id, so real artwork on the device is never touched.
- Strokes are injected with `UiAutomation.injectInputEvent`, using
  `MotionEvent.TOOL_TYPE_STYLUS`, pressure, and historical samples at 240Hz, to exercise batching.
- The screenshot tests need the brush panel buildable without an Activity. If `BrushPanel` cannot be
  hosted in the screenshot runtime, capture those states with an instrumented test on the emulator
  profile instead, and record which method was used.

## Risks and mitigations

- **AGP 9.1 compatibility of screenshot libraries.** Mitigation: the Executor checks compatibility
  first. The fallback is instrumented screenshot capture with a pixel-diff script in `tools/`.
- **Device variance.** Mitigation: the protocol's warm-up, thermal and iteration rules, and results
  compared only on the same device.

## Acceptance criteria

1. `DEVICES.md` and `PROTOCOL.md` are committed and approved by the product owner.
2. All five macrobenchmarks run on the flagship reference device, and their JSON is committed with the
   commit SHA, device and protocol version.
3. `TraceSectionMetric` reports `Stroke.process` p50/p95/p99 for the three stroke scenarios.
4. Screenshot tests produce the agreed matrix and run from a clean clone on Linux with one command.
   Re-running without code changes gives zero diffs.
5. The latency protocol has been executed once on the stylus device and the median recorded.
6. `BASELINE-<date>.md` lists every metric against its target in `ACCEPTANCE_CRITERIA.md` with
   pass/fail, and is linked from `docs/STATUS.md`.

## Automated test matrix

Everything in scope items 3, 4 and 6. The screenshot suite and JVM tests join the required gate. The
macrobenchmarks run on demand and before each phase is accepted.

## Device/manual test matrix

Scope item 5, plus one manual confirmation per device that the benchmark build did not touch the
